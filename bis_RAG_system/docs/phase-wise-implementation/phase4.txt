# Phase 4: Specialized Sub-flows — Detailed Description

## Objective

Phases 1-3 built one general-purpose grounded Q&A pipeline. But several of the problem statement's required capabilities aren't actually Q&A problems — they're **structured lookups or decision trees that happen to be wrapped in natural language**. Routing every query through the same "retrieve chunks → generate grounded prose" flow would be both slower and less accurate for these cases than just querying the structured tables Phase 1 already built for them. Phase 4 identifies which queries should skip RAG entirely and hit structured logic instead, and builds those flows.

The design principle: **use RAG only where the answer is genuinely unstructured prose (clause text, FAQ explanations). Everywhere the underlying data is already tabular (product→standard mapping, lab directory), query it directly — it's more accurate, cheaper, and impossible to hallucinate.**

---

## Step 12: Product → Standard Recommender

This is the flow with the biggest accuracy stakes: an MSME asking "do I need certification for my LED bulbs" needs a yes/no answer backed by the actual CRS/QCO list, not an LLM's best guess from similar-sounding product descriptions.

Design: a **structured intake, not free-text RAG**, for the core lookup. The user's product description gets matched against `product_standard_map` (the table Phase 1 built but hasn't populated from a real scrape yet — this is a direct dependency that needs closing before Phase 4 can actually ship). Matching itself can't be exact string match (nobody types the official BIS product category verbatim), so this needs either:
- fuzzy/full-text search against `product_name` using the GIN index already in the schema, or
- an embedding-based match against product names specifically (a much smaller, cleaner embedding space than the full document corpus from Phase 2)

The output is deterministic once a match is found: mandatory/voluntary status, the applicable IS number, and the scheme name — pulled straight from the table row, not generated. Where the match is ambiguous (multiple plausible products, or no confident match), the flow should say so explicitly and offer the closest candidates rather than picking one silently — this is the same confidence-gate principle from Phase 3, applied to structured lookup instead of retrieval.

---

## Step 13: Certification Process Guide

Unlike the recommender, this flow's content is genuinely known and mostly static: BIS publishes discrete, nameable schemes (ISI Mark/Scheme-I, CRS/Scheme-II, FMCS, Systems Certification, Scheme-X), and Phase 1 already scraped an overview + FAQ page for each.

Design: **pre-built structured walkthroughs, one per scheme**, triggered by intent detection identifying which scheme the user is asking about. Each walkthrough is a step-by-step sequence (application → document prep → inspection/testing → grant → renewal) with the specific figures Phase 1 already surfaced attached at the relevant step — e.g., the ₹1,000 application fee and ₹7,000/man-day inspection fee from the verified Product Certification FAQ slot into the "Apply" and "Inspection" steps respectively, rather than being left for the LLM to recall or worse, approximate.

This is deliberately **less dynamic than the general Q&A flow** — the tradeoff is intentional. A first-time applicant benefits far more from a clear, correct, pre-verified sequence than from a fluent paragraph that might subtly misorder steps or blend two schemes' requirements together. The general RAG flow from Phase 3 remains available for follow-up questions that don't fit the walkthrough shape ("what if my factory changes address mid-application" — which, incidentally, is Q.25 in the FAQ content already scraped).

---

## Step 14: Lab Locator

Pure structured query, no LLM involvement in producing the answer itself: filter the `labs` table (schema ready since Phase 1, but not yet populated — same dependency gap as the product mapping table) by location and testing scope, using the `idx_labs_state` and `idx_labs_scopes` indexes already defined.

Worth flagging again from Phase 1: the richest lab data source (`lims.bis.gov.in`, 431 labs with per-lab test-facility detail, including the "search labs by IS number" endpoint that's especially valuable here) is JS-rendered and still needs its underlying API identified. Until that's done, this flow can only run against the static Group-1/Group-2 PDF exports, which have less granular per-lab test-scope data. This directly limits how precise a "which lab can test my product against IS 1786" answer can be right now.

---

## Step 15: Consumer Query / Complaint Handling

A distinct intent branch, not a variant of the general Q&A flow, because the right response shape is different: consumer complaint questions ("my hallmarked jewellery seems underweight, what do I do") need a **process pointer, not an explanation**, and critically, complaint intake itself must never be reimplemented by the assistant — Phase 1's research surfaced that BIS already runs a real complaint-management system of record (BIS CARE app, or the manakonline.in Standard Promotion Portal). The assistant's job here is to correctly identify complaint-shaped queries and route to the real channel (with the relevant detail — e.g., the compensation formula from the consumer hallmarking FAQ: 2x the purity shortfall value, plus testing charges) rather than attempt to process anything itself.

Tone also shifts for this branch: a consumer asking about a possible quality issue is a different register than an MSME asking about certification procedure, and the response should reflect that (more reassuring, less procedural density) even though both draw on the same underlying grounded-answer machinery from Phase 3.

---

## Step 16: Intent Router

All four sub-flows above, plus the general Q&A flow from Phase 3, need a dispatcher in front of them: a lightweight classifier or rule-based router that reads the incoming query and decides which flow handles it, before any retrieval happens. This has to run first and cheaply — it's the thing that lets Step 12's product lookup skip RAG entirely rather than wastefully retrieving hallmarking FAQ chunks for a CRS product question.

Given the category taxonomy Phase 1 already built into the corpus (`product_standard_mapping`, `certification_process`, `certification_faq`, `lab_directory`, `hallmarking`, `consumer`, `training`), the router's job is really just to map a query onto that same taxonomy — meaning it can likely reuse Phase 2's Step 7 category-filtering intent classification directly, rather than needing separate logic. Worth checking whether that's true in practice before building it twice.

---

## What Phase 4 depends on from Phases 1-3

- `product_standard_map` and `labs` tables — schemas exist since Phase 1, but **neither has been populated from a real scrape yet**. This is the single biggest blocker to shipping Steps 12 and 14 as anything more than an empty structure.
- The category taxonomy from Phase 1's `sources.yaml` tagging, reused for intent routing (Step 16)
- Phase 3's confidence-gate pattern, reapplied to structured-lookup ambiguity (Step 12) rather than retrieval uncertainty
- The exact fee/procedure figures already verified in Phase 1's FAQ scraping (₹1,000, ₹7,000/man-day, 90-day validity, 2x compensation formula) — Step 13's walkthroughs and Step 15's complaint guidance should embed these directly rather than re-deriving them

## What's genuinely uncertain going in

- Whether fuzzy/full-text matching is good enough for the product recommender, or whether it needs the embedding-based approach — this can't be answered without the product mapping table actually being populated and tested against realistic, messy product descriptions (nobody says "Crystalline Silicon Terrestrial Photovoltaic module," they say "solar panel")
- Whether the intent router genuinely reuses Phase 2's category filter or needs distinct logic — flagged above as worth checking rather than assuming
- How much the certification walkthroughs (Step 13) need to differ from just showing the scraped FAQ content directly — there's a real risk of building a parallel, harder-to-maintain structure that duplicates what Phase 1 already scraped in a different shape
