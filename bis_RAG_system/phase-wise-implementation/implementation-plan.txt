Phase 1: Data Foundation (Week 1)
Identify and scope data sources — BIS website (bis.gov.in), IS standards catalog, CRS/QCO product lists, hallmarking scheme docs, BIS Care portal FAQs, lab recognition directory. Note which are downloadable PDFs vs HTML pages vs need manual compilation.
Build the scraper/ingestion scripts — separate scrapers for structured data (product-code-to-standard tables, lab directory with location/capability) vs unstructured docs (standard PDFs, scheme explainer PDFs).
Clean and chunk documents — parse PDFs preserving clause/section numbers (use PyMuPDF or pdfplumber, not raw text dump). Chunk by clause boundary, tag each chunk with metadata: IS number, revision year, product category, mandatory/voluntary status.
Store raw + processed data — raw PDFs in blob storage, processed chunks + metadata in a structured DB (Postgres) that mirrors the vector DB records for auditability.
Phase 2: Retrieval Pipeline (Week 2)
Set up vector DB (Qdrant or Weaviate) and embed chunks using a multilingual embedding model (BGE-M3 or similar) so Hindi/regional-language queries work later.
Build hybrid retrieval — dense vector search + BM25 keyword search in parallel, since IS numbers and product codes are exact-match-sensitive and embeddings alone miss them.
Add metadata filtering + reranking — filter by product category/standard type before reranking top candidates with a cross-encoder, so the LLM only sees highly relevant, correctly-scoped chunks.
Test retrieval quality standalone — before touching the LLM, verify: given "what standard applies to LED bulbs," does it actually surface the right IS number? This is the part worth debugging hardest, since a wrong retrieval poisons everything downstream.
Phase 3: Generation Layer (Week 3)
Prompt engineering for grounded answers — system prompt that forces citation of IS number + clause for every factual claim, and explicit refusal/hedging language when retrieval confidence is low.
Build the confidence/refusal gate — a lightweight check (retrieval score threshold, or a self-consistency check) before the LLM commits to an answer, so it says "I'm not fully certain — please verify against BIS's official portal" rather than guessing.
Implement citation formatting — responses should show "As per IS XXXX:YYYY, Clause X.X" with a link/reference back to the source doc, not just prose claims.
Phase 4: Specialized Sub-flows (Week 3-4)
Product → standard recommender — structured intake (product description or category dropdown) that queries the product-code-to-standard table directly rather than relying purely on free-text RAG, since this needs to be exact, not fuzzy.
Certification process guide flow — pre-built structured walkthroughs (ISI mark, hallmarking, FMCS) triggered by intent detection, rendered as step-by-step UI rather than a wall of text.
Lab locator — simple filtered search over the lab directory (location + testing capability), no LLM needed here, just structured query.
Consumer query handling — separate intent branch for complaint/grievance-type questions (different tone, points to BIS Care/consumer helpline rather than technical standards).
Phase 5: Multilingual Support (Week 4)
Query translation layer — detect input language, translate to English for retrieval (or use multilingual embeddings directly if quality is good enough to skip translation).
Response translation — translate generated answer back, but keep IS numbers/clause references untranslated (they're identifiers, not prose).
Test on Hindi + at least one regional language end-to-end for retrieval accuracy, not just fluency.
Phase 6: Frontend + Integration (Week 5)
Chat UI with source citations shown inline/expandable, plus a structured fallback search panel for users who prefer browsing over chatting.
Intent router — a lightweight classifier or rule-based router at the front that sends queries to the right sub-flow (general Q&A vs product recommender vs certification guide vs lab locator).
Feedback loop — thumbs up/down on answers, logged with the retrieved chunks, so you can show a "how do we improve" story in the demo.
Phase 7: Testing & Demo Prep (Week 6)
Build a test set of realistic queries across personas (MSME owner, student, consumer) and measure retrieval accuracy + citation correctness manually.
Stress-test edge cases — ambiguous product descriptions, outdated standard queries, mixed-language input.
Prepare demo script highlighting the grounding/citation feature specifically — that's the differentiator judges will care about over a generic chatbot wrapper.

The single highest-leverage thing to get right early is Phase 1-2 (data + retrieval) — a hackathon demo lives or dies on whether the retrieved standard is actually correct, not on how polished the chat UI looks.
