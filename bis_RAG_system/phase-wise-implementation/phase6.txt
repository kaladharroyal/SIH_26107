# Phase 6: Frontend + Integration — Detailed Description

## Objective

Phases 1-5 built a correct, grounded, multilingual answer-generation pipeline — but it currently only exists as backend logic. Phase 6 is where that becomes something a user actually interacts with, and where all the specialized sub-flows from Phase 4 (product recommender, certification walkthroughs, lab locator, consumer complaint routing) get unified behind a single interface rather than existing as separate scripts. The design principle here: **the chat interface is the default surface, but it should never be the only way to get an answer** — because Phase 3's confidence gate means some queries will legitimately come back uncertain, and a user shouldn't be stuck rephrasing a chat query when a structured search would get them there directly.

---

## Step 19: Chat UI with Inline Citations

The core interface is conversational, but citations from Phase 3 need to be genuinely usable, not just present. Concretely:
- Every factual claim's citation (IS number + clause, or FAQ source) renders as an expandable/clickable element, not just a plain-text tag at the end of a paragraph — so a user can verify a specific claim without losing their place in the conversation.
- Citations link back to the actual source: for FAQ-derived answers, the original bis.gov.in URL captured in Phase 1's manifest; for clause-derived answers, ideally the specific page of the source PDF (using the `page_start`/`page_end` fields Phase 1's parser already attaches to every chunk).
- The distinction Phase 3 established between FAQ-sourced (BIS's own simplification) and clause-sourced (the regulation itself) citations should be visually distinct — not just textually different — since conflating them risks a user treating a simplified gloss as having the same authority as the standard text.

**Structured fallback search panel**: alongside the chat, a simpler filtered-search interface exists for users who'd rather browse than converse — this maps directly onto Phase 4's structured sub-flows (product lookup, lab locator by location/scope) which don't need conversational framing at all and arguably work better as direct filters. This isn't a lesser version of the assistant; for a user who already knows they want "labs in Guntur that test electronics," a filter UI is strictly faster than typing a sentence and waiting on retrieval.

---

## Step 20: Intent Router → UI Routing

Phase 4's intent router (Step 16) already decides which backend sub-flow handles a query. Phase 6 extends that same routing decision to the *frontend*: a product-recommender-routed query should render as a structured result (mandatory/voluntary badge, IS number, scheme name — pulled straight from the table per Phase 4's design) rather than as a paragraph of generated prose describing the same three facts. A certification-process query should render as the step-by-step walkthrough UI (naturally suited to `step_card`-style rendering) rather than a wall of text describing the same sequence.

This matters beyond aesthetics: forcing every sub-flow's structured output through prose generation reintroduces exactly the hallucination surface Phase 4 was designed to eliminate by bypassing RAG for tabular data. If the UI renders raw structured data directly, that guarantee holds all the way to what the user sees; if everything gets prose-ified for display, an LLM formatting pass could still introduce an error even though the underlying data was correct.

---

## Step 21: Feedback Loop

Every answer gets a lightweight thumbs up/down, logged against `query_logs` (the table Phase 1's schema already provisioned specifically for this, including `retrieved_chunk_ids` and `confidence_score` columns) — meaning this step has near-zero new schema work, just wiring the UI action to an existing insert.

The value here is diagnostic, not just a vanity metric for the demo: because each feedback entry is tied to the specific chunks that were retrieved, a pattern of thumbs-down on a particular chunk or category is a direct signal of exactly which part of the Phase 1-2 pipeline needs attention — a bad chunk boundary, a miscategorized source, or a systematically low reranker score for a legitimate query type. This is also the natural place to close Phase 3's open calibration question (where to set the confidence threshold) with real usage data instead of a guessed number.

For the hackathon demo specifically, this is worth surfacing explicitly to judges: it's the mechanism that turns "we built a chatbot" into "we built a system that gets measurably better," which is a meaningfully different and stronger claim.

---

## What Phase 6 depends on from Phases 1-5

- Phase 4's intent router output, reused directly for UI routing (Step 20) rather than re-classified — if Phase 4 confirmed the router can be shared between backend dispatch and category filtering (flagged as worth checking, not yet confirmed), the same reuse question applies here a third time
- Phase 1's `page_start`/`page_end` metadata on every chunk — this is what makes "link to the specific page" in Step 19 possible instead of just "link to the PDF"
- Phase 1's `query_logs` schema — built ahead of need specifically so this step wouldn't require new migration work
- Phase 5's citation-span preservation — the clickable citation UI in Step 19 needs the IS number/clause number to have survived any translation pass character-for-character

## What's genuinely uncertain going in

- Whether the structured fallback panel (Step 19) is worth building for a hackathon timeline versus just polishing the chat flow — this is a scope tradeoff, not a technical unknown, and depends on how much of Phase 4's sub-flow work is actually finished by this point
- Whether real users engage with thumbs up/down at meaningful volume without prompting — feedback loops are notorious for having very low voluntary engagement, which would mean Step 21's diagnostic value stays theoretical rather than actually informing threshold calibration during the hackathon window itself
- Whether page-level PDF linking (Step 19) is worth the engineering effort of hosting/serving the manual_standards PDFs with page-anchor support, versus just linking to the document and stating the page number in text — a reasonable de-scoping if time is tight
