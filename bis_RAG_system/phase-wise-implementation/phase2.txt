# Phase 2: Retrieval Pipeline — Detailed Description

## Objective

Phase 1 produced clause-tagged chunks sitting in Postgres — correctly structured, but not yet searchable by meaning. Phase 2 turns that structured text into a retrieval system that can take a plain-language query ("do I need certification for my LED bulbs") and surface the right clauses, FAQ entries, or scheme documents with high precision.

The core design tension in this phase: **BIS content is exact-match-sensitive AND meaning-sensitive at the same time**. A query like "what's the fee for renewing my BIS licence" needs semantic matching (the user won't say "annual licence fee" exactly), but a query containing "IS 1786" needs exact-match precision — embeddings alone routinely fail on alphanumeric codes because they get tokenized oddly and don't cluster meaningfully in vector space. So Phase 2 is built around **hybrid retrieval** from the start, not semantic search with keyword search bolted on later.

---

## Step 5: Vector Database Setup

**Choice: Qdrant or Weaviate over a managed/hosted option like Pinecone.**

The reason is metadata filtering, not raw search speed. Every chunk from Phase 1 carries rich metadata — `is_number`, `part`, `revision_year`, `category` (certification_faq, hallmarking, lab_directory, etc.), `mandatory` flag. Retrieval needs to filter on this *before* the semantic search runs, not after — e.g., a hallmarking query should never surface a chunk tagged `category: fmcs_faq`, regardless of how semantically close it scores. Qdrant and Weaviate both support this "filtered ANN search" natively; some hosted options make it an afterthought.

**Embedding model: a multilingual model (BGE-M3 or similar), not an English-only one.**

This is decided now, not deferred to the multilingual phase later — because re-embedding an entire corpus after the fact is expensive and because BGE-M3 specifically supports **hybrid dense+sparse retrieval in one model call**, which maps directly onto the hybrid approach below. Choosing an English-only embedding model now would mean redoing all of Phase 1's embedding work when multilingual support gets built.

Each `clauses` row from Phase 1 gets embedded and upserted with its Postgres `chunk_id` as the vector DB's point ID — this is what makes a retrieval hit traceable back to the exact SQL row, source PDF, and page range.

---

## Step 6: Hybrid Retrieval

Two retrieval paths run in parallel on every query, then get merged:

**Dense (semantic) search** — the query gets embedded with the same multilingual model and searched against the vector index. This is what handles paraphrased, plain-language queries ("how do I get my product certified" matching a chunk titled "Certification Process").

**Sparse (BM25/keyword) search** — runs against Postgres's full-text index (already set up in Phase 1's schema: `idx_clauses_text_search`). This is what catches exact IS numbers, clause references, and scheme names that dense embeddings miss or under-weight.

The two result sets get merged with **reciprocal rank fusion** rather than a fixed weighted average — RRF is more robust when one method returns zero relevant hits (which happens routinely: a query with no IS number in it gives BM25 almost nothing useful, while a query that's *just* an IS number like "IS 1786" gives dense search a bad, near-meaningless embedding to work with).

---

## Step 7: Metadata Filtering + Reranking

Before results reach the LLM, two more passes tighten precision:

**Metadata pre-filtering** — using the query's detected intent (product lookup vs. certification guide vs. hallmarking vs. lab locator — this intent classification is a small, fast step, either rule-based keyword matching or a lightweight classifier) to restrict the search to the relevant `category` values before ranking runs. This prevents a hallmarking question from ever seeing FMCS chunks, independent of vector similarity.

**Cross-encoder reranking** — the top ~20-30 candidates from the hybrid search get rescored by a cross-encoder (which jointly encodes query+chunk together, unlike the bi-encoder used for the initial retrieval), and only the top 3-5 go to the LLM. Bi-encoder similarity is a fast but coarse approximation; the cross-encoder pass catches cases where two chunks look similar by cosine distance but one actually answers the question and the other doesn't.

---

## Step 8: Standalone Retrieval Testing

This step happens **before any LLM generation work** — deliberately, because a wrong retrieval poisons every downstream layer, and it's far cheaper to catch and fix at this stage than after a generation pipeline is built on top of it.

The test method: build a small set of realistic queries per category (e.g., "what standard applies to LED bulbs", "how much does hallmarking testing cost", "is CRS registration mandatory for laptops") and manually verify — for each one — that the top retrieved chunk is actually the correct clause/FAQ entry, not just topically related. Given the FAQ content verified in Phase 1 (28 real Q&A pairs from the Product Certification page, similar structure across hallmarking and consumer FAQs), this is a good testbed: FAQ chunks have unambiguous "correct answer" ground truth, unlike prose clause text where relevance can be fuzzier.

Concretely worth checking:
- Does an IS-number-containing query correctly favor BM25/exact-match results over semantically-similar-but-wrong ones?
- Does the reranker actually improve ordering over raw hybrid fusion, or is it just adding latency? (Worth A/B checking on a small query set rather than assuming.)
- Do category filters ever incorrectly exclude the right answer because intent classification misfired?

---

## What Phase 2 depends on from Phase 1

- Clause-level chunks with metadata (`is_number`, `category`, etc.) — the filtering step is only as good as this tagging
- The FAQ Q&A splitting from `scrape_html_page` — since FAQ chunks are the cleanest ground truth for testing retrieval quality
- The Postgres full-text index already defined in `schema.sql` — no new schema work needed for the BM25 side, just a query layer on top
# What's genuinely uncertain going in

- Whether BGE-M3's Hindi/regional-language embedding quality is good enough to skip a separate translation step (Phase 5 territory, but the embedding choice here determines the answer) — needs actual testing against real Hindi BIS content, not assumed
- Whether reranking is worth its latency cost for a live chat interface vs. batch-testing only — this is a product tradeoff, not a technical one, and depends on how snappy the demo needs to feel
